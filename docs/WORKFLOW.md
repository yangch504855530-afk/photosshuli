# photosshuli 标准开发流程(SOP)

本仓库的所有变更——无论来自谁的提议——都走同一条流水线。**提出者只需一句话,流程自动走到发布,中途不停下来等催促。**

## 触发方式(对开发代理/AI 说一句话即可)

| 你说 | 触发 | 版本号 |
|---|---|---|
| `需求: <描述>` | 完整闭环:需求评审 → 开发 → 测试 → 回流 → 发布 | +0.1(minor) |
| `回流: <问题/缺陷>` | 缺陷修复闭环:复现先行 → 修复 → 全量回归 → 发布 | +0.0.1(patch) |
| `发布` | 仅把当前 HEAD 走门禁后发布 | 不变 |

## 流水线五阶段

```
① 需求/问题提出 ──► ② 产品评审 ──► ③ 研发实现 ──► ④ 测试验证 ──► ⑤ 发布
                        │                            │
                        ├── 驳回(记录理由)            └── 失败 → 回流③(最多3轮)
                        └── 采纳(写验收标准)                 └── 仍失败 → 停下,带完整上下文上报
```

### ① 提出
一句话即可,但必须包含:想要什么 + 大概场景。代理负责补全成用户故事与验收标准。

### ② 产品评审(采纳/驳回都要有理由)
- 每条需求给出:**采纳/驳回 + 理由 + 验收标准**(可测试的)。
- 本项目的**产品底线**(驳回依据,不重复讨论):
  1. 人在环:AI/自动规则只能建议,删除/移动的执行权在人,且必须先预览;
  2. 可回滚:任何"删除"=移入 `_PhotosShuli回收站`,永不真删;
  3. 密钥/隐私不出本机:API Key 只存本地,上传内容需显式同意;
  4. 无外部依赖降级:没有网络/Key/ffmpeg 时,功能必须能用本地规则跑通。

### ③ 研发实现
- **缺陷修复必须测试先行**:先写一个"失败中的复现测试",修复后它必须转绿;
- 破坏性/不可逆操作前(如覆盖用户文件)需确认现状与预期一致;
- 遵循现有架构:引擎(photosshuli/*.py)与 UI(web/index.html)分离;所有用户路径来自运行时输入,禁止硬编码。

### ④ 测试验证(回流闭环)
- 全量测试套件必须 **100% 绿**:`python -m unittest discover -s tests`
- 新功能必须带新测试;回流修复必须带上那个"复现测试";
- 失败 → 回到③修复 → 再跑(最多 3 轮),仍失败则停下并带完整上下文上报提出者。

### ⑤ 发布(门禁脚本强制)
```bash
python scripts/check.py        # 三道门禁,全部通过才能发布
git add -A && git commit && git push
git archive --format=zip -o <zip> HEAD
gh release create vX.Y.Z --title "..." --target main --notes-file <notes> <zip>
```
发布门槛(`scripts/check.py` 自动检查):
1. 全量测试通过;
2. **个人路径/密钥泄漏扫描**通过(硬编码路径、key 等不得出现在仓库);
3. **版本一致性**:config.VERSION 与 README 中版本标记一致,且 `v{VERSION}` 标签未被占用。

发布说明(release notes)必须包含:新增/修复清单、测试结果、已知限制。

## 工程约束(对所有参与者生效)

- 测试离线可跑(不打真实 API、不依赖 ffmpeg 存在);
- 决策/索引等状态写入 `.photoshuli/`(已 gitignore);
- 中文 UI;提交信息英文一行式;
- 版本三处同步:config.VERSION、README 更新段、git tag。
